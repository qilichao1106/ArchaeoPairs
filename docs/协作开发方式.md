# 考古器物图 Pair 构造项目协作开发方式（L0）

> 依据：《ClaudeCode-Codex-dsh 日常开发方法论 v1.0》（2026-11-20 读）
> 项目：ArchaeoPairs — 考古报告器物图 Pair 数据构造
> 日期：2026-11-20
> 结论：先按 **L0 + C 档** 跑通证据链——1 个实现者（Codex）+ 1 个独立验证者（dsh）+ Claude 编排，WIP=1；不并行、不建平台、不上内核。

---

## 1. 为什么是 L0

方法论的三问：

1. **任务可独立并行吗？** 当前没有产品代码、没有契约冻结、视觉链路强耦合，切不出两两不相交的 allow。并行即冲突。
2. **单 agent 基线低于 45% 吗？** 尚无基线。先跑 5–10 张卡，记录成功率/返工/token/墙钟，再决定是否扩围。
3. **有真实并行空间吗？** 单人评审带宽 = 1，WIP=1 已足够。

因此：**L0 + C（脚本/台账 advisory，关键门禁机检）**。升级到 L1 的条件：连续两波吞吐高于单 agent、allow 可切分、人工介入 <3 次/日；否则维持 L0。

## 2. 角色与工具

| 角色 | 默认工具 | 只做 | 绝不 |
|---|---|---|---|
| Sponsor / Approver | 人 | 定目标、批预算、批破坏性变更、接受风险、拍板停用 | 不绕过证据链、不口头批准 |
| Orchestrator | Claude Code（本会话）+ 人 | 写 AC/计划/任务卡/契约、派单、审 diff、串行合并、生成日报 | 不写产品代码、不替实现者修 bug、不替验证者写断言、不用自然语言宣布"通过" |
| Implementer | Codex（dsh 可按卡替换） | 按卡实现、自检、handoff | 不改卡外文件、不改 contracts/tests、不直改 main、不自己宣布通过 |
| Verifier | dsh（独立 Claude 会话可替换） | 独立按 AC 写冻结测试、跑测试、负向对照、出机读报告 | 不改产品代码、不放宽/删除/跳过断言、不与实现者共享会话 |

硬约束：
- **同一张卡的实现者 ≠ 验证者**；
- 验证者不继承实现者会话上下文，只拿卡 + AC + handoff 工件；
- 门禁判定只来自退出码 / 结构化比较 / 哈希，不来自 LLM 总结。

## 3. 本机工具事实（2026-11-20 实测）

### 3.1 Codex CLI 0.169.0

- 入口：`codex exec`；`--json` JSONL；`-o` 落盘；`resume`/`fork` 续跑。
- Provider：`~/.codex/config.toml` 中 `model_provider = "maas_deepseek"`，
  `model = "deepseek-v4.1-flash-1017"`，`wire_api = "responses"`，
  base URL 为阿里云 MaaS 的 OpenAI 兼容端点。
- 事实约束：`exec` 下审批硬编码 Never，**派单前 G1 必须查完 allow/预算**；
  沙箱写不了 worktree 的 `.git` → 实现者把变更留工作区，由编排者**代提交**并保留 `[T-xxx] [codex]` 标注。
- 冒烟：`codex exec --json -o /tmp/codex_smoke.jsonl --sandbox read-only "只回复 OK" < /dev/null` → 返回 `OK`。

### 3.2 dsh（DeepSeek Harness）0.2.2-rc.1

- 入口：`dsh --profile headless --json "任务"`；`--session-id` 续跑。
- Provider：`~/.dsh/profiles/headless/cordis.patch.yml` 的 `dashscope` 指向同一 MaaS
  兼容端点，默认模型 `deepseek-v4.1-flash-1017`。
- 凭据：`DASHSCOPE_API_KEY` 已写入 Windows 用户环境变量（新开终端生效）；
  当前 shell 可用 `export DASHSCOPE_API_KEY=...` 临时注入。密钥不入仓库、不进日志。
- 冒烟：`dsh --profile headless --json "只回复 OK" < /dev/null` → `text: "OK"`。

### 3.3 Claude Code 2.1.329

- 承担 Orchestrator：写卡、派单、审 diff、代提交、合并、日报。
- 需要脚本化时用 `claude -p ... --output-format json`，本阶段不用。

### 3.4 三工具 headless 命令

```bash
# 实现（Codex）
codex exec --json -o artifacts/<task>/codex.jsonl \
  --sandbox workspace-write "<implementer prompt>" < /dev/null

# 验证（dsh）
DASHSCOPE_API_KEY=... dsh --profile headless --json \
  "<verifier prompt>" < /dev/null

# 编排（Claude，可选）
claude -p "<orchestrator prompt>" --output-format json
```

## 4. 协作工件与唯一写者

| 路径 | 作用 | 唯一写者 |
|---|---|---|
| `AGENTS.md` / `CLAUDE.md` | 行为契约（单一真源；CLAUDE.md 仅 `@AGENTS.md` 导入） | 人（Claude 起草、人审定） |
| `Plan.md` | 里程碑 + 可机检验收命令 | Orchestrator（人确认里程碑） |
| `IMPLEMENT.md` | 决策与偏差日志（只追加） | Orchestrator |
| `collab/cards/T-xxx.md` | 任务卡（唯一授权） | Orchestrator；执行者只读 |
| `collab/board.json` / `events.jsonl` | 状态台账 / 追加事件流 | Orchestrator |
| `collab/inbox/<agent>/` | 单向信箱（handoff / question / report） | 发送方 |
| `collab/artifacts/<task>/` | 自检/测试/冒烟证据 | 实现者/验证者各写本任务 |
| `contracts/` | 数据契约（ArtifactMap / PairRecord / 报警码 / JSON Schema） | Orchestrator |
| `specs/` | 场景 WHEN/THEN 与 AC crosswalk | Orchestrator |
| `tests/`、`qa/`、`fixtures` | 冻结验收测试与测试资产 | Verifier |
| `selfcheck/` | 实现者自检（与 qa 分离） | Implementer |
| `worktrees/<agent>/<task>/` | 隔离工作区（不入库） | 各 agent 只在本树作业 |
| `src/` | 产品代码（卡内 allow 精确路径） | Implementer |
| `docs/mh/` | 执行基线/env/覆盖/NFR/runbook | Orchestrator |
| `.env`、`keys/`、`*.pem` | 凭据 | 无 agent 写权（DENY） |

新增路径先在本表登记角色与写者，再进 AGENTS.md；**未登记的路径默认谁都不许写**。

## 5. 任务卡模型

卡头（机检）+ 正文（场景/备注）。L0 必填：

```yaml
id: T-001
title: <一句话行为增量>
stream: pipeline
owner: codex
verifier: dsh
allow: [src/archaeopairs/ingest/xml.py, tests/... ]   # 精确路径，同波不相交
accept: [AC-01]
non_goals: ["不引入跨图合并"]
goal: <可观察行为>
stop_condition: "python -m pytest tests/qa/T-001 -q::0"  # 命令 + 期望退出码
max_files: 10
max_lines: 400
max_depth: 0
max_rounds: 3
budget: {tokens: 200000, wall_minutes: 90}
deps: []
```

状态（L0 简化）：`proposed → ready → claimed → implementing → handed_off → verifying → passed → merged → archived`，异常 `blocked / rejected / cancelled`。卡号永不复用。

## 6. 日常闭环（每张卡）

1. **定义 AC**：Orchestrator 与人在 `specs/` 写 WHEN/THEN，AC 编号进 Plan。
2. **写卡**：`collab/cards/T-xxx.md`，填 allow / non_goals / stop_condition / budget / deps。
3. **G0/G1 预检**：`python scripts/preflight.py`（Windows 可 `scripts\doctor.cmd`）退出 0；基线文件存在；allow 非空且同波不相交；non_goals 非空；deps 已 merged；stop_condition 可执行。
4. **隔离工作树**：
   ```bash
   git worktree add worktrees/codex/T-xxx -b codex/T-xxx
   ```
5. **派单给 Codex**（附录 B.2 提示词 + 卡路径）；实现者只改 allow 内文件。
6. **自检 + handoff**：selfcheck 退出 0，日志落 `artifacts/T-xxx/`；handoff 写 branch / commit / files / cmd 三元组 / cwd / risks / verifier_entry / unfinished。
7. **代提交**（Codex 沙箱写不了 `.git` 时）：
   ```bash
   git -C worktrees/codex/T-xxx add <allow 内文件>
   git -C worktrees/codex/T-xxx commit -m "feat(<scope>): <summary> [T-xxx] [codex]"
   ```
8. **派验证给 dsh**：新 worktree 从 `handoff.branch` 拉取，不继承实现会话：
   ```bash
   git worktree add worktrees/dsh/T-xxx -b qa/T-xxx codex/T-xxx
   ```
   验证者只写 `tests/qa/`，按 AC 写冻结测试，跑真实 `N passed; M failed`，做负向对照，出 report。
9. **G3/G4/G5**：
   - G3：verifier ≠ owner；report.commit == handoff.commit；AC 全 pass；至少一条负向对照；copy-proof 含 `worktrees/dsh/T-xxx`。
   - G4：`git diff` ⊆ allow；HEAD == 签署 commit；handoff 后无追加提交。
   - G5：合并后全量回归退出 0；main 红则停线。
10. **合并 + 归档**：串行合并、打 `merge/T-xxx-<date>` tag、证据归档、更新 board/coverage。

失败去向：返工（≤3 轮，必答"根因/改了什么/为何这次会过"）→ blocked 升级人类；连续两轮同样失败 → 重写场景/AC。

## 7. 本项目的测试与验收模型

数据管线的判定不能靠"看起来对"，冻结为四类：

1. **契约测试**：`ArtifactMap` / `PairRecord` / 报警码的 pydantic/JSON Schema 校验。
2. **黄金样例**：手工标注的小图 + XML 片段 → 期望 `ArtifactMap`（JSON 快照）与期望 PNG 的像素/哈希。
3. **不变量测试**：每个序号要么入 Unit、要么入 `unbound_*`；一器物一 Unit；每 Unit 至少一比例尺或报警；内容区纯平移。
4. **负向对照**：注入真实故障（删掉一个 seq 映射、错绑比例尺、破坏掩膜），测试必须由绿转红。

首批 AC 草案（设计定稿后冻结）：

| AC | 内容 |
|---|---|
| AC-01 | 四类图路由到四条工作线，L4 零 Pair |
| AC-02 | 多器物线图按序号硬匹配生成 Unit，1:1 / N:1 / 1:N / N:N 四类关系正确 |
| AC-03 | 比例尺三级绑定，来源 L1/L2/L3 落盘；共享尺复制到每个 Unit |
| AC-04 | 单器物线图/版图整图直通，01 命名 |
| AC-05 | 成图白底、纯平移、2%–5% 留白、比例尺行置底 |
| AC-06 | 未映射/缺视图进入 `unbound_*` 并转复核，不静默丢弃 |
| AC-07 | 命名规则（图号提取、冒号归一、_N 去重、后缀保留） |
| AC-08 | 全量回归 + 负向对照通过 |

指标：映射覆盖率 100%（入 Unit 或 unbound）、一器物一 Pair、比例尺来源可追溯率 100%、成图纯平移自检通过率 100%。

## 8. 门禁（L0 最小集）

| 门 | 判定 | 失败动作 |
|---|---|---|
| G0 规范门 | 基线/契约/specs 存在且非空 | 不派单 |
| G1 授权门 | allow 精确且不相交、non_goals 非空、deps merged、预算已留 | 不派单 |
| G2 自检门 | selfcheck 命令退出 0，commit == 分支 HEAD，handoff 字段齐 | 返工 |
| G3 验证门 | verifier ≠ owner、AC 全 pass、nodeid 可解析、负向对照、copy-proof | 返工 |
| G4 合并门 | diff ⊆ allow、HEAD == 签署 commit、无 handoff 后提交 | 不合并 |
| G5 回归门 | 全量回归退出 0、scope 声明、非 0 tests | main 不变、停线 |

门禁脚本变更须 Approver 签字；被约束者不得改约束。

## 9. 安全与密钥

- API Key 只存在用户级配置/环境变量：`~/.codex/config.toml`、Windows 用户环境 `DASHSCOPE_API_KEY`；**不入仓库、不进任务卡、不进 prompt、不进日志**。
- `.env`、`keys/`、`*.pem` 在 `.gitignore` 与 agent DENY 清单。
- 每次派单前检查：prompt 中无 key、handoff 中无大段日志、artifact 中无凭据。
- 备份：改配置前已生成 `*.bak-20261120`；如需回滚，恢复对应文件即可。
